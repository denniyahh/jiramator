# Jiramator

## What This Is

Jiramator is a config-driven CLI for bulk Jira ticket automation. `plan` generates a
Program Increment's worth of epics/tickets from YAML templates, `import` bulk-creates
issues from CSV/XLSX, and `update` bulk-edits existing issues from CSV/XLSX. Everything
is preview-first (`--dry-run` never touches Jira). It's for product owners, scrum
masters, and tech leads running PI planning — not necessarily programmers; first-time
setup is a guided `jiramator init` wizard.

## Core Value

Eliminate repetitive manual Jira issue creation/editing during PI planning and bulk
data intake, without ever surprising the user — every operation shows a preview before
touching Jira.

## Context

- Brownfield Python CLI, five-layer architecture (CLI → Config → Builder → Client →
  Planner, with a parallel Importer/Updater path) — see repository `CLAUDE.md` for the
  authoritative architecture description.
- Two-tier config model: `configs/org/` (Jira URL, field ID mappings, aliases; shared
  across a company) and `configs/teams/` (project key, epic/ticket templates; per-team,
  changes every PI). Real configs are gitignored; `.example` variants are tracked.

## Constraints

- **Compatibility**: Python 3.11+ (CI matrix: 3.11/3.12/3.13 × Linux/macOS/Windows) —
  no runtime dependency that breaks on any of these.
- **Security**: Jira credentials never stored in config files — read from env vars
  (`JIRA_EMAIL`/`JIRA_TOKEN` by default, overridable per-org).
- **Distribution**: primary install path is `pipx install git+...` — no PyPI package
  today; a signed/notarized binary would be needed for locked-down corporate machines,
  which is currently out of scope.
- **Network**: must degrade gracefully (not fail) when Jira is unreachable during
  `--dry-run` for `plan`/`import`; `update --dry-run` is the one exception and requires
  live credentials outright.
