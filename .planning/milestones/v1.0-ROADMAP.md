# Roadmap: Jiramator

**Created:** 2026-04-27
**Depth:** Coarse (3-5 phases, 1-3 plans each)
**Coverage:** 10/10 v1 requirements mapped

## Overview

Jiramator's current milestone extends the working PI planning CLI with reliability features (error recovery, reporting), config power (template inheritance), and a new MCP entry point. Phases are ordered by dependency: foundation enables MCP (needs non-interactive mode + execution reports), and template inheritance is independent but logically precedes MCP's broader audience exposure.

## Phases

### Phase 1: Reliability & Robustness

**Goal:** Users can trust bulk operations to fail gracefully, report clearly, and resume without data loss.

**Dependencies:** None (builds on existing working code)

**Requirements:** FOUND-01, FOUND-02, FOUND-03, IMPT-01

**Success Criteria:**
1. User sees specific field name and line number in error messages when YAML validation fails
2. User receives a structured report (issues created, skipped, errors) after every plan or import run
3. User can re-run a failed bulk creation and only the uncreated issues are attempted
4. User can import a Windows-exported Excel file (cp1252 encoding) without manual conversion

**Plans:** 5/5 plans complete
- [x] 01-01-PLAN.md — FOUND-01: line-aware YAML loader, ConfigValidationError, did-you-mean suggestions, ticket_builder line-marker strip
- [x] 01-02-PLAN.md — IMPT-01: encoding detection module (BOM → UTF-8 → charset-normalizer), spreadsheet.py integration
- [x] 01-03-PLAN.md — FOUND-02 substrate: run_report.py module (RunReport, IssueResult, atomic write, find_resumable, hash)
- [x] 01-04-PLAN.md — FOUND-02 + FOUND-03 integration: _template_key in ticket_builder, planner.py + importer.py emit-and-consume reports
- [x] 01-05-PLAN.md — CLI wiring: --report, --resume, --force, --encoding flags; ConfigValidationError + ConfigDriftError handlers; e2e tests

### Phase 2: Template Inheritance & Sprint Assignment

**Goal:** Users can eliminate repetitive config by inheriting org defaults into team configs, and assign sprints declaratively.

**Dependencies:** Phase 1 (actionable validation errors support debugging inheritance issues)

**Requirements:** TMPL-01, TMPL-02, ISSUE-01

**Success Criteria:**
1. User defines shared fields in org config and team config inherits them without repeating
2. User can fill in fields not locked by org or team defaults via per-template `fields:`, and team defaults flow into all team templates without repetition
3. User can specify sprint assignment in config and created tickets land in the correct sprint (config/flag-driven, non-interactive)

### Phase 3: Accessibility (pivoted from MCP Server Integration)

**Goal:** Non-technical users can get set up and run Jiramator without
hand-editing YAML or learning raw Jira field IDs. _(Original goal — "interact
via MCP protocol" — was reviewed and declined; see the pivot note below.)_

**Dependencies:** Phase 1 (non-interactive execution, execution reports), Phase 2 (template inheritance available to MCP callers)

**Requirements:** INTG-01, INTG-02, INTG-03

**Success Criteria:**
1. User can invoke plan and import operations via MCP tools from any MCP-compatible client
2. MCP tools execute without interactive prompts (fully non-interactive)
3. MCP and CLI produce identical Jira issues given the same inputs
4. MCP tools return structured JSON results (not Rich-formatted text)

**Progress notes (2026-07-10):**
- The **planner input/execution split landed early** (the "planner refactor
  bundled into Phase 3" decision). `run_plan` now accepts a `PlanInputs` object
  and `assume_yes`, so plan runs fully non-interactively; `_collect_plan_inputs`
  is the only interactive edge. CLI exposes `--pi-number`, `--versions`, `--yes`.
  This **satisfies INTG-02** at the CLI level.
- **Front-end spike:** a `workflow_dispatch` GitHub Actions form
  (`.github/workflows/jiramator-plan.yml`) drove the non-interactive CLI. Found
  **unusable** for the target audience — GitHub Actions is disabled by
  enterprise/org policy (no Actions tab, dispatched runs never get a runner).
  Docs moved to the wiki (`Running-via-GitHub-Actions`).

**PHASE 3 PIVOT — MCP declined, accessibility delivered via wizard (2026-07-10):**
- `docs/mcp-server-proposal.md` was **reviewed and declined** as the primary
  accessibility path: MCP does not remove the real on-ramp barriers (install
  Python, mint token, hand-edit YAML with raw field IDs) — a user would need all
  of those *plus* an MCP client.
- **INTG-01 (MCP server) and INTG-03 (identical results): DECLINED**, retained as
  possible future work only.
- The accessibility goal was met by the **`jiramator init` setup wizard**
  (CONF-01, v1.1.0): connects to Jira, auto-discovers custom field IDs,
  validates the project, sets up credentials, writes both config files. Ships
  with wiki walkthrough; README leads with `init` + `pipx`.
